= Product Capability Audit: Retailing
:revdate: 2026-09-21

== Boundary verdict

Retailing should own the sellable/listing projection of catalog data: what is offered, in which commercial/store context, and with which publication state. It must not become the source of truth for catalog structure, pricing, stock, shipping, or generic tenant identity.

== Capability matrix

[cols="3,1,4",options="header"]
|===
|Capability |Status |Audit
|Sellable listing identity |PARITY |Existing Retail entities and listing-kind vocabulary show a real sellable projection.
|Publication lifecycle |PARITY |Canonical publish/unpublish lifecycle now includes optional effective publication windows without introducing a second workflow state.
|Catalog linkage |PARITY |Retail kinds already map to catalog-owned vocabulary.
|Storefront facet projection |PARITY |Retailing consumes Cataloging facet_contracts through CatalogSearchServiceInterface and does not duplicate Faceting counting/filter semantics.
|Store/channel scoping |PARITY |Retailing now uses canonical owner/vendor identity only; the legacy tenantId alias has been removed from active Retailing placement state.
|Assortment/listing eligibility |PARITY |Eligibility is explicit and deterministic: lifecycle/window, canonical catalog ownership, and owner scope produce auditable reason codes used by storefront and marketplace matching.
|Merchandising placement |PARTIAL |Only if placement is retail-specific; generic presentation belongs elsewhere.
|Price reference |PARITY |Retailing consumes typed Pricing `PriceQuoteDTO` results, validates listing reference/currency, and projects quoted or negotiated amounts into Ordering intent without owning price calculation.
|Stock/availability reference |PARTIAL |Reference Stocking availability; do not own quantities.
|Shipping eligibility reference |PARTIAL |Retailing no longer emits tenantId, while Shipping still exposes a broader legacy tenantId contract that requires its own migration before direct handoff can be green.
|Scheduled publication |PARITY |Published listings support optional start/end effective windows, and storefront/vendor-service queries exclude not-yet-effective or expired listings.
|===

== Boundary risks

* Shipping still exposes a broader active tenantId contract; migrate that downstream contract independently before wiring Retailing placement directly into Shipping.
* Avoid duplicating Cataloging taxonomy or Pricing/Stocking engines.
* Keep seller/vendor identity in Vendoring.

== Milestone direction

First milestone: canonical listing + publication lifecycle and owner/vendor references.
Second milestone: channel/store assortment eligibility and scheduled publication.
Third milestone: deterministic pricing/stock/shipping projection contracts.
Storefront integration milestone: Retailing-side tenantId compatibility removal and Cataloging/Searching facet projection acceptance are COMPLETE; downstream Shipping identity-contract migration remains separately owned.
